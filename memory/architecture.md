## The service boundary (the load-bearing idea)

`arch.md` §5.

```
pages → hooks → SellerService (typed interface) → adapter
```

Three adapters satisfy one interface:

| Adapter | File | When it is used |
| --- | --- | --- |
| Demo | `seller/services/mockSellerService.ts` | No Supabase env. Browser-local, seeded, labelled. |
| Supabase | `seller/services/supabaseSellerService.ts` | Both `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` set. |
| — | `createSellerService()` in `sellerService.ts` | The only place the choice is made. No third behaviour, no silent fallback. |

Every read returns `dataSource: 'demo' | 'live'`. `capabilities` declares what the backend can do:

```ts
interface ServiceCapabilities {
  auth: boolean
  oauth: boolean   // separate from auth on purpose — see decisions.md
  uploads: boolean
  database: boolean
}
```

## Layering rules (from `arch.md` §9 — do not violate)

1. **`features/seller` must not import from `features/storefront`.** The storefront may depend on the
   seller module; never the reverse.
   - Checkable: `grep -rn "features/storefront" src/features/seller/` returns nothing.
2. **Consumers of the seller contract may import exactly two things:** `lib/seller.ts` and
   `getSellerService`. Nothing else. Never seller pages or components.
   - Checkable: `grep -rn "features/seller" src/features/try-on/` returns only those.
3. **`lib/` must not import from `features/`.** `lib/seller.ts` imports only `lib/catalog`.
4. **Pages never import an adapter.** Pages import hooks; hooks import `SellerService`.
5. **No secret enters `src/`.** Only `VITE_`-prefixed public config.
6. **Ownership is enforced in the database.** Client filtering is presentation, not security.

## Routing

`src/routes/paths.ts` is the single source for every URL — nothing writes a URL as a string literal.
Public paths are generated by `lib/catalog` because QR codes, copy-link buttons and the storefront
must agree character-for-character.

| Group | Paths |
| --- | --- |
| `marketing` | `/` · `/get-started` · `/sign-in` |
| `onboarding` | `/onboarding/store` · `/onboarding/ready` · `/onboarding/products` |
| `seller` | `/seller/dashboard` · `/collection` · `/products` · `/products/new` · `/products/:id/edit` · `/store` · `/analytics` · `/settings` |
| `public` | `/:storeSlug` · `/:storeSlug/p/:productId` · `/p/:productId` (resolver) · `/tryon/:productId` · `/tryon/lab` |

## Data flow — the two directions

**Seller writes.** Page → hook → `SellerService.createProduct(...)` → adapter → (demo: `localStorage`
via `mockDb.ts` / live: `products` table + `try-on-assets` storage).

**Customer reads.** `PublicProduct`/`PublicStore` → `usePublicCatalog` → `getSellerService()` →
`resolveProduct(id)` / public store read → the `storefront_products` / `storefront_stores` views
(anon key, safe columns only, signed-out works).

`/tryon/:productId` reads through the same public path — `resolveProduct(productId)` — and never
touches seller-private fields.

## Documentation contract

`arch.md:3-6` — *"When a decision changes, change it here in the same commit."* A change to the
architecture, the schema, the route table, or the `Product` contract is not finished until
`arch.md` and, where relevant, `design.md` and `task.md` say the same thing. **This memory directory
